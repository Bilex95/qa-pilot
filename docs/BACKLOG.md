| BL-014 | **High priority.** Invite token in URLs. The Stage 3 accept screen (`frontend/src/modules/orgs/components/invite-accept.tsx`) sends a signed out visitor to `/login?next=/invite/<token>` and `/register?next=/invite/<token>`, and the token is also in the page path `/invite/<token>` and the API path `GET /invitations/{token}`. A token in a URL leaks through browser history, server and proxy logs, and the Referer header sent to other sites. Proposed fix: (1) keep the return target out of the query string: store it in `sessionStorage` (tab scoped, removed on use, accepted only as a same origin relative path) and use plain `/login` and `/register` links; (2) put the token in the URL fragment (`/invite#<token>`, never sent to a server or in Referer) and send it to the API in a POST body (`POST /invitations/preview`, `POST /invitations/accept`), keeping the old paths for one release; (3) add `Referrer-Policy: no-referrer` and `Cache-Control: no-store` on the invite and reset pages. Stage: batch 4B with I-23, because password reset links (D-045) need the same handling and should not copy the current pattern; I-21 (security review) verifies it. **Done in I-23 (D-055):** fragment links, POST body endpoints, no token in the access log, the token kept in `sessionStorage` of the tab for 30 minutes, the old routes removed, `Referrer-Policy: no-referrer` and `Cache-Control: no-store` on the invite, reset and forgot password pages. I-21 (security review) verifies it | I-10 |
